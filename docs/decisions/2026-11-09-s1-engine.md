# S1 adds snowballstemmer, keeps scikit-learn and XGBoost out, and accumulates in float64

owner: architect · date: 2026-11-09 · status: decided · class: engineering

Decided by the architect within the founder's delegation for this session (coordinator's S1 brief: "add it to
requirements.txt; record that"; "no sklearn unless you record it"; "a small numpy GBDT or a documented stand-in is
fine on CPU").

**Decision.**
1. **`snowballstemmer` joins `requirements.txt`.** It is the prototype's stemmer (Porter, pure Python, no
   dependencies). The analyzer `s3_english` is the prototype's word pattern, stopwords and stemmer.
2. **No scikit-learn, no SciPy.** The dense model in development, `tfidf-svd-<d>`, is TF-IDF with a randomized SVD
   (3 power iterations, a fixed seed, a deterministic sign) written in numpy (`engine/encode.py`). It is fitted on the
   host at build and stored in the segment, so every device encodes queries the same way.
3. **No XGBoost on CPU.** The ranker is a small histogram GBDT in numpy (`engine/rank/gbdt.py`): squared loss on the
   graded labels E=3, S=2, C=1, I=0, NaN in its own bin. It is a **pointwise stand-in** for the prototype's XGBoost
   ranking objective. The training-recipe fix (judged candidates, plus random unjudged candidates as negatives, never
   the top unjudged) is in `engine/rank/train.py` and is independent of the learner. Any model with `predict(X)` can be
   registered with `Index.add_ranker`, so XGBoost can come back in Colab without touching the engine.
4. **float64 accumulation, float32 results.** BM25F's segment sums and the dense matmul accumulate in float64 and
   round to float32. A row's scores then do not depend on the batch it is in (`search_batch == [search]`), and agree
   across numpy and torch to the last bit in the CPU tests. A float32 GEMM is an S6 fast path, checked against this.

**Why.**
- CI is CPU-only, numpy-only and has a 60 s budget; each dependency left out is one less install and one less thing
  that differs between CI and Colab. `snowballstemmer` is the exception because parity with the prototype (0.304 and
  title-only parity against OpenSearch) depends on the exact stemmer, and it is a single pure-Python wheel.
- The steward's contract checks `search_batch == [search]` and the same response twice; float32 BLAS results change
  with the batch shape (seen here: a 1-ULP difference failed that check before the change).

**Alternatives.**
- *scikit-learn's TfidfVectorizer and TruncatedSVD.* Familiar, but a large dependency (with SciPy) for two functions,
  and its tokenizer is not ours. Rejected.
- *XGBoost with `rank:ndcg` on CPU.* The prototype's learner; a 200 MB wheel for CI. Rejected for CI; fine in Colab.
- *A LambdaMART in numpy.* Closer to the prototype's objective, more code to get right now. Deferred: S3 or the lab's
  ranking research may add it behind the same `predict` interface.
- *float32 accumulation with tolerance in the batch check.* Faster on GPU, but the contract's exact check would need
  a carve-out. Rejected for the reference; allowed as a fast path.

## Objections

- evaluation-steward (anticipated): "A pointwise ranker will not reproduce the prototype's GBDT numbers." Answer:
  agreed, and it should not try: the prototype's GBDT hurt ranking (0.167 against RRF's 0.319). S1-7 reproduces the
  lexical 0.304 and RRF; the ranker is judged on its own predictions in Colab.
- platform-engineer (anticipated): "float64 on GPU halves dense throughput." Answer: on an A100 FP64 is fast enough
  for exact search at 1.2M x 384 in batches; S6 owns the float32 path and must pass the same contract within its
  tolerance.
- Founder: none raised (delegated).
